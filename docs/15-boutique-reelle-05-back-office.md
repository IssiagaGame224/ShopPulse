# 15 — Vraie boutique, phase 5 : le back-office

> **Contexte.** Phase 5 : la boutique s'administre. Gestion des commandes (statuts),
> gestion du catalogue (création/édition de produits), le tout réservé au rôle
> `stock-manager`. Au passage, le modèle produit est **enrichi** (SKU, prix barré,
> caractéristiques) en préparation de la refonte design (phase 6 du plan produit,
> inspirée des fiches e-commerce type joutech.ma).

## Le modèle produit enrichi

```csharp
public record Product(int Id, string Name, string Category, decimal Price, int Stock,
    string ImageUrl, string Description, string Sku, decimal? OldPrice,
    IReadOnlyList<string> Features)
{
    public bool IsOnSale => OldPrice is { } old && old > Price;
}
```

- **Sku** : référence commerciale unique (`SP-0001`…), index unique en base ;
- **OldPrice** : prix barré quand le produit est en promo (un produit seedé sur cinq) ;
- **Features** : caractéristiques en liste à puces (style fiche e-commerce), stockées en
  colonne **`jsonb`** — l'ordre est préservé, pas de table jointe pour une simple liste.

Persistance : `Id` passe en **identity PostgreSQL** (`UseIdentityColumn`,
`GENERATED BY DEFAULT` : le seed insère ses ids 1..200 explicitement, les créations
reçoivent un id automatique).

**Piège — séquence identity désynchronisée.** La migration qui ajoute l'identity sur une
table déjà peuplée crée la séquence… à 1 : la première création entre en conflit avec le
seed (`23505 duplicate key PK_products`). La migration inclut le recalage :

```sql
SELECT setval(pg_get_serial_sequence('products', 'Id'),
              COALESCE((SELECT max("Id") FROM products), 0) + 1, false);
```

## L'API d'administration

Groupe `/api/admin` protégé par la politique **`CanManageStock`** (claim `role` du JWT,
rôle realm Keycloak `stock-manager` — déjà propagé depuis la phase 4) :

| Endpoint | Rôle |
|---|---|
| `GET /admin/orders?status=` | Toutes les commandes, filtre par statut (400 si inconnu) |
| `PUT /admin/orders/{id}/status` | Transition validée + email client |
| `POST /admin/products` | Création (id identity) |
| `PUT /admin/products/{id}` | Mise à jour complète |

Contrôle d'accès vérifié : **401** anonyme, **403** avec un jeton sans rôle
(l'utilisatrice `client`), **200** avec `demo` (stock-manager).

### Transitions de statut : une machine, pas un champ libre

```
Pending ──→ Paid ──→ Shipped        (terminales : Shipped, Cancelled)
   └──→ Cancelled ←──┘
```

Une commande ne « recule » jamais ; une transition interdite → **409** avec message ;
réécrire le même statut est idempotent (200). Chaque transition réussie déclenche un
**email client** (`IOrderEmailSender.SendStatusChangedAsync`, capturé par Mailpit en
dev) — toujours en try/catch : le SMTP ne bloque jamais l'administration.

### Validation produit côté serveur

Partagée création/mise à jour : SKU et nom obligatoires, prix > 0, stock ≥ 0, **prix
barré > prix** (sinon refusé — une « promo » qui augmente le prix n'a pas de sens),
catégorie existante, **SKU unique** (vérifié + index unique en filet). Toute écriture
invalide le tag de cache `catalog`.

## Le back-office (feature RCL `ShopPulse.Features.Admin`)

- `/admin/orders` (InteractiveServer) : tableau des commandes (référence, date, client,
  total, statut), filtre par statut, boutons d'action contextuels (« Marquer payée »,
  « Marquer expédiée », « Annuler ») ;
- `/admin/products` : tableau du catalogue (SKU, prix, prix barré, stock) + sous-navigation
  Commandes ↔ Produits ;
- `/admin/products/new` et `/admin/products/{id}/edit` : `EditForm` complet (catégorie en
  liste déroulante alimentée par l'API, caractéristiques « une par ligne »), erreurs de
  validation serveur affichées telles quelles.

Double garde : `[Authorize(Policy = "CanManageStock")]` appliqué au **routage**
(`AuthorizeRouteView`, phase 4) pour l'UI, et la même politique côté API pour les
données — masquer un bouton n'a jamais été une sécurité. Le lien « Back-office » du
menu n'apparaît que pour le rôle (`AuthorizeView Roles="stock-manager"`).

## Vérifications effectuées

- Build solution 0/0 ; architecture **14/14** ; **E2E 3/3** (invité, compte, admin) ;
- migration appliquée sur la base existante (produits enrichis : `SP-0005`, promo

- **E2E admin** (`AdminE2eTests`) : login `demo` → commande créée en amont passée à
  « payée » via le bouton → édition du prix du premier produit → prix relu dans la liste ;
- emails de statut visibles dans Mailpit.

## Bilan des notions

- une machine à transitions pour les statuts : le domaine interdit, l'API traduit en 409 ;
- `jsonb` pour les listes simples : ni table jointe, ni ordre perdu ;
- identity sur table peuplée : toujours recaler la séquence dans la même migration ;
- la même politique protège l'UI (routage) et l'API (données) — jamais l'une sans l'autre ;
- l'enrichissement du modèle précède le design : les pages publiques (phase suivante)
  consommeront SKU, promos et caractéristiques sans nouvelle migration.

**Prochaine étape** : refonte design complète (fiche produit, catalogue, accueil,
panier/checkout) dans le style e-commerce de référence, en consommant les champs
enrichis ; puis phase 6 — paiement Stripe.
